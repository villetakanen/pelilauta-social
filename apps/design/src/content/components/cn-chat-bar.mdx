Use CnChatBar to give a reader one authoring surface for a Markdown reply that stays
reachable while the conversation it answers keeps scrolling.

## When to use it

Mount it as a direct child of the application chrome your page already renders; it has
no placement of its own outside that container, and an astro-island standing between
the two carries no layout of its own either.

Use it wherever a reader composes a reply. Where a message has already been sent, its
presentation is [CnBubble](/components/cn-bubble)'s, not this component's.

## Example

The consumer binds `value`, supplies `label` and `placeholder`, and receives a send
intent through `onsend`. Sending neither clears the draft nor removes the bar, so a
failed write keeps what the reader typed.

<Composition caption="A consumer binding value, receiving a send intent, and rendering leading and trailing actions plus supporting content">
  <ChatBarDemo client:load />
</Composition>

```svelte
<script>
  import CnChatBar from '@design-system/components/CnChatBar.svelte'

  let value = $state('')
  function onsend(draft) {
    // report or persist draft; value is untouched until the consumer changes it
  }
</script>

<CnChatBar bind:value label="Vastaa keskusteluun" placeholder="Kirjoita viesti..." {onsend}>
  {#snippet leading()}<button type="button">…</button>{/snippet}
  {#snippet trailing()}<button type="button">…</button>{/snippet}
</CnChatBar>
```

The component is an island: without `client:load`, or the framework's equivalent, Enter
sends nothing and the draft never leaves the textarea.

The bar renders no leading or trailing action of its own — `leading`, `trailing` and
`supporting` are consumer-supplied regions, and every control placed in them is a
native button under [Links, Actions and Buttons](/base/links-actions-buttons); the bar
attaches no role or keyboard handler to them.

The bar stands at its container's block end and grows with the draft until it reaches the
application bar. Two presentations ship, driven by the surrounding `app-chrome` container
rather than the browser window: below the small breakpoint it spans the container, and
past it the bar is inset and centred.

## Reference

### Props

| Prop | Type | Purpose |
| :--- | :--- | :--- |
| `value` | `string` | Bindable. The draft. Defaults to an empty string. |
| `label` | `string` | Required. The textarea's accessible name. Localise it; the placeholder does not repeat it. |
| `placeholder` | `string` | The prompt shown while the draft is empty. |
| `disabled` | `boolean` | Renders the textarea immutable and every supplied action inoperable. Defaults to `false`. |
| `onsend` | `(value: string) => void` | Reports a send intent carrying the current value. Runs on Enter, never on Shift+Enter or during text composition, and never for a value that is empty or only white space. |
| `supporting` | `Snippet` | Context above the input row: an attachment preview, a write error. |
| `leading` | `Snippet` | Actions at the input row's inline start. |
| `trailing` | `Snippet` | Actions at the input row's inline end. |

## Accessibility

The textarea's accessible name is `label`; a consumer supplies and localises it, and the
placeholder names nothing. `disabled` marks the textarea and every supplied leading and
trailing action inoperable, so a supplied button needs no separate `disabled` attribute
to match. Keyboard focus on the textarea draws the shared focus ring without moving or
resizing anything around it.
