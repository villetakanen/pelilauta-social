# Audit of Epic 165 and PR 168

## Task as set

Review the implementation of [epic #165](https://github.com/villetakanen/pelilauta-social/issues/165) in [PR #168](https://github.com/villetakanen/pelilauta-social/pull/168). Establish the remaining application gap against the existing implementation, identify unnecessary implementation and verification, and propose a smaller delivery. Stop at analysis. The operator subsequently requested this report file; implementation and mitigation remain unauthorized for this run.

The epic describes the desired thread-reading capability. The operator states that most of that capability already existed and expected a small correction to subscription triggers and SSR. Tests should cover added or changed application behavior, with minimal setup and assertions. One concise test per relevant scenario is reasonable; neither a universal test-count limit nor exhaustive coverage of the epic is required.

The operator confirms that restoring Firestore ordering followed explicit steering. The removal is evidence of operator correction, not autonomous recognition by the implementation agent.

## Summary

The implementation lost the distinction between a capability that must hold and work the application must perform to make it hold. It replaced existing Firestore ordering, added viewport restoration, and built tests around both. Later deletions reduced those additions but left an unused module, weak verification, and defects in the SSR-to-live transition. The subscription guard addresses only part of anonymous page execution. The evidence supports a failure of task interpretation and orchestration scope control. Existing instructions were also reportedly ignored; missing guidance cannot explain the whole run.

Prefer a selective restart of #165 from its pre-implementation baseline after clarifying the goal and correcting the specific harness defects. Preserve unrelated release work, accepted decisions, and the audit evidence. Do not retain all new skills or specs automatically: some encode the interpretation that caused the expansion. A restart means a reviewed reversal of selected changes on the active branch, with history retained, followed by a bounded implementation. It does not mean deleting the release branch or resetting shared history.

## Findings

### The anonymous execution boundary remains incomplete

**High priority; the claimed outcome is not delivered.** `apps/pelilauta/src/threads/server/DiscussionApp.astro:13` unconditionally uses `client:load`. That renders initial HTML but also hydrates the entire discussion for anonymous readers. Astro documents that [`client:load` loads and hydrates immediately](https://docs.astro.build/en/reference/directives-reference/#clientload).

`apps/pelilauta/src/threads/client/ReplyArticle.svelte:152` mounts `ReactionButton` for every reply. `apps/pelilauta/src/components/svelte/app/ReactionButton.svelte:76` performs a Firestore `getDoc` on mount without an active-session guard. Hiding the button's markup at line 142 does not prevent its mount callback. The opening-post reaction island also mounts unconditionally at `threads/server/ThreadInfoSection.astro:123`.

`ReplyArticle.svelte:49` calls `getProfileAtom` whenever prepared attribution is absent. The profile store starts a Firestore read at `stores/profiles/index.ts:48`. This includes an unresolved author in the initial response, rather than exclusively a newly arrived live reply. It also introduces a browser-oriented store side effect into server rendering.

The anonymous browser test at `e2e/anonymous-visitor-live-reading.spec.ts:93` records every Firestore request. That is useful evidence of browser data access, but does not distinguish a one-shot read from a continuing application subscription. Its result cannot by itself localize an `onSnapshot` leak. The reaction mount is a concrete source of unnecessary reads; the historical count of Listen requests was not reproduced in this audit.

The page also inherits unconditional client islands from `layouts/Base.astro:54`, `:87`, and `:105`, the client router in `components/server/BaseHead/BaseHead.astro:78`, and the composer at `pages/threads/[threadKey]/index.astro:85`. Consequently, the strict site-wide near-zero-JavaScript tenet was not satisfied before this PR either. Do not describe a subscription guard as achieving it, or silently expand this correction into a site-wide rendering rewrite.

### The first live snapshot can remove existing author attribution

**High priority; introduced by this implementation.** `DiscussionSection.svelte:138` rebuilds every snapshot entry as `{ reply }`, discarding prepared author and HTML fields. Keyed rendering retains the existing `ReplyArticle` instances.

`ReplyArticle.svelte:49` initializes `liveAuthorAtom` once. For an initially attributed reply, that value is `undefined`. When the first snapshot removes `preparedAuthor`, the derived author at line 52 has neither attribution source. The reply then renders the anonymous label and loses its avatar and profile link.

Compiling the actual component with the installed Svelte compiler reports `state_referenced_locally` at lines 49 and 51. This supports the source trace; no browser reproduction was performed. Svelte documents the warning as [capturing only the initial reactive value](https://svelte.dev/docs/svelte/compiler-warnings#state_referenced_locally).

The same snapshot drops every prepared body. `ReplyArticle.svelte:56` initially holds an empty fallback body and renders Markdown asynchronously. Thus the first live handoff unnecessarily reparses unchanged replies and permits an empty intermediate body. The observed author defect and this rendering transition deserve more attention than tests of unchanged reply counts.

### The new SSR reply path carries unsanitized author HTML

**High priority; an existing renderer defect reaches the new server-rendered surface.** `threads/server/prepareDiscussion.ts:51` passes reply Markdown through `utils/marked.ts`, and `ReplyArticle.svelte:181` injects the result as HTML. The renderer performs no sanitization. A local invocation with inert example script text returned the script element unchanged. Marked explicitly states that [it does not sanitize output](https://marked.js.org/#usage).

PR #168 records the shared problem as #166. This audit does not attribute the original renderer defect to #165. However, moving replies into initial document markup changes their execution context and carries that defect into the new SSR path. The JSON-LD escaping test does not establish safety of the rendered reply body; its browser fixture disables JavaScript. Production exploitability and response security policy were not tested.

### Platform replacement survived as dead code and test overhead

**Confirmed removable code.** `threads/readingAnchor.ts:13` exports `selectReadingAnchor`, but the only importer is `test/threads/readingAnchor.test.ts:10`. Its 36 implementation lines and 46 test lines serve no production path. The final refactor's commit message incorrectly says anchor selection remains in use.

Commit `7f0ae48f` removed the existing Firestore `orderBy`, introduced a comparator, and added 81 lines of comparator tests. Commit `3b527ea1` introduced viewport measurement and `window.scrollBy` restoration, accompanied by three browser tests totaling 267 lines. Commit `f195461a` removes those implementations and tests after operator steering.

The remaining `e2e/re-anchor-a-deleted-reading-target.spec.ts:59` still infers an application-selected reading anchor from viewport visibility, even though the selector module is unused. The focus transfer is actual application code and can merit a small check if retained. Native viewport clamping and generic scroll behavior do not justify a separate application mechanism or a large fixture.

### Subscription lifecycle management duplicates framework responsibilities

**Reduction opportunity.** `DiscussionSection.svelte:59` maintains a subscribed account, an unsubscribe callback, a generation counter, a termination function, and two effects. The `account` parameter of `subscribeToReplies` is unused. The post-registration generation check at line 152 adds a second race check around synchronous registration.

Svelte already runs an effect's returned cleanup before rerunning and on destruction, as documented in its [effect lifecycle](https://svelte.dev/docs/svelte/$effect#Understanding-lifecycle). One account-dependent effect can hold the unsubscribe callback and an attempt-local cancellation flag. The asynchronous import still requires cancellation handling; deleting that protection would introduce a real race. Capture the thread key and active account synchronously, register after the import only if the attempt remains active, and return cleanup from the same effect.

This is a smaller ownership model for the application's listener, not a proposal to test Svelte's lifecycle implementation.

### The profile API refactor serves no SSR caller and changes failure semantics

**Unnecessary scope with a behavior change.** `firebase/server/profiles.ts:18` introduces `getProfileData`; its only consumer is the existing REST route. SSR uses the separate `getPublicProfiles` function. The stated justification that SSR and the route now share a profile accessor does not match the call graph.

The new helper catches read and parsing errors and returns `null`. `pages/api/profiles/[uid].json.ts:13` converts that to 404, conflating a failed backend read with a missing profile. Reversing this extraction removes unrelated code and its tests. Retaining a public-profile schema outside the browser store and a batched public-attribution read is justified by SSR.

### Data normalization changes widen the correction and leave inconsistencies

`utils/client/entryUtils.ts:32` changes a shared conversion function used by 55 call sites. `schemas/ThreadSchema.ts:93` also changes missing-date behavior. Preserving unknown dates is a reasonable requirement, but the current tests demonstrate selected thread examples rather than the shared change's reach. Truthiness checks do not handle all invalid dates, and spreading the original entry retains falsey stored date values instead of consistently omitting them.

`schemas/ReplySchema.ts:33` makes creation time mandatory across all reply consumers. The ordered query at `firebase/server/discussion/fetchDiscussion.ts:47` already excludes records lacking that field. Firestore documents this [field-existence behavior](https://firebase.google.com/docs/firestore/query-data/order-limit-data#orderBy_and_existence). The schema amendment is not needed to obtain query ordering; retain it only as an explicit data-contract decision.

The current replies spec accepts exclusion of undated records. The original spec carried fallback ordering. This is a product-policy change, not merely a refactoring. Git records the amendment but cannot establish the conversation that approved it. The changelog still claims undated replies produce an incomplete-content notice, which the query cannot produce for documents it never returns.

`DiscussionSection.svelte:133` sets `incomplete` on a malformed snapshot record but never clears it on a later fully valid snapshot. The per-snapshot status should describe the current snapshot if that behavior remains in scope.

### Several tests cannot prove their stated claims

- `e2e/resolve-session-after-render.spec.ts:62` checks that existing IDs remain present before and after fixed waits. It passes if the live subscription never starts and does not establish that it starts once. Its premise that a reload always starts with inactive session state also conflicts with the persisted `active` state in `stores/session/index.ts`.
- `e2e/preserve-chronology-after-an-edit.spec.ts` reads an already edited fixture. It performs no live edit and therefore does not establish the transition its scenario names.
- `e2e/terminate-a-live-subscription.spec.ts` demonstrates sign-out behavior only. The scenario also names account changes and page departures. A new write after sign-out is not a reproduction of an already queued late callback.
- `e2e/compose-thread-page.spec.ts` adds a login flow and detailed layout assertions around largely unchanged page composition.
- `test/threads/server/prepareDiscussion.test.ts` mocks all three collaborators and mainly asserts assembly and flag forwarding. The real SSR test supplies stronger evidence for the introduced outcome.
- `test/threads/server/latestReplyFragment.test.ts` uses three module mocks and 64 lines to check a final-element lookup and an empty fallback. Existing page assertions can verify the selected destination.
- The `3b527ea1` commit message claims both initial-read and live-listener failure branches are unit-tested. Only the server-read failure test was found. `e2e/README.md:26` names that server test without supplying evidence for the live error callback.

These are fidelity and duplication problems. Seven useful scenario tests would be proportionate. The current replies spec has ten scenarios, eight browser tests, and two failure scenarios without browser tests; total browser growth across all three specs is seventeen tests. Those counts alone do not determine which tests should survive.

### Secondary correctness and record issues remain

`threads/server/discussionMetadata.ts:140` sets the interaction count to the number of metadata-eligible comments. Omitting a comment because its author is unknown does not remove the visible reply, so that count can understate the conversation it describes.

`DiscussionSection.svelte:195` retains the pre-existing one-time read-state lookup and 300 ms unread-navigation timer. It does not implement the new read-state spec's delayed-session and cancellation rules. PR #168 acknowledges this gap; it is not evidence that #165 is complete.

The PR records an app-bar overlap failure for reply fragments. That is an application CSS integration concern, rather than a reason to reimplement fragment navigation. It was not reproduced in this audit.

`threads/server/QuoteBubble.astro:19` remains client-only after its move. Quoted reply content therefore remains outside the complete anonymous SSR claim. The file's behavior predates this work.

## Root cause and contributing artifacts

### The implementation did not establish what already satisfied the goal

The strongest evidence is the replacement of an existing ordered Firestore query with client sorting, followed by restoration after steering. The same pattern appears in custom viewport correction and an attachment link added in `ef5cab86` and removed in `46e5b284`. The implementation treated constraints as a list of mechanisms to create.

That supports a task-interpretation failure. It does not reveal the agent's internal understanding, prove prompt leakage, or isolate a particular model as the cause. The available self-assessment is a secondary account, not an execution transcript.

### The test rule expanded without a changed-behavior inventory

`.claude/skills/app-e2e/SKILL.md:8` requires one test per scenario, and line 12 associates tests with slices that implement behavior. That rule is compatible with the operator's expectation when applied to the actual delta. Commit `bdb9db9f` instead expanded verification across the surrounding capability, carrying repeated login, project checks, comments, and fixtures.

The missing step was identifying which scenarios changed, which already held, and which depended entirely on platform behavior. An arbitrary cap on tests would not repair that omission.

### Orchestration did not stop drift, and model guidance was reportedly ignored

`.claude/skills/first-mate/SKILL.md:8` requires delegation of every implementation, check, and prose pass. Lines 21–25 check spec readiness and then direct implementation. They do not require identifying the remaining baseline gap before delegation.

The operator confirms that first-mate is intentionally an orchestration-only role. It should detect drift and stop work that exceeds the brief. The proposal to permit inline implementation was withdrawn because it changed that role without addressing its scope-control failure.

The operator reports that the Claude Code/Opus 5.5 run ignored existing model-selection instructions. The skill names the cheapest model capable of the task, and `CLAUDE.local.md:7` directs selection of the fastest model for the task. These instructions already existed. The reported noncompliance is distinct from a missing rule; no invocation trace was independently inspected to establish which models ran or what effect a different selection would have had.

Delegating oversized work can amplify its cost, but the evidence does not establish that mandatory delegation caused the drift. The untracked delivery self-assessment reports approximately fifteen subagents and repeated operator arbitration, but those counts were not independently verified.

### Existing restraint was not applied consistently

`docs/WRITING.md` already prohibits prose that repeats code or platform documentation. `specs/TEMPLATE.md:20` already rejects derivable statements. The implementation added long comments explaining data fields, framework behavior, and test scenarios anyway. Examples include `DiscussionSection.svelte:52`, `ReplyArticle.svelte:19`, `prepareDiscussion.ts:7`, and the copied scenarios at the start of most browser tests.

Missing instructions cannot fully explain a failure to apply instructions already present. More prose and more mandatory gates would risk reproducing the same problem.

### The assessment skill itself biases diagnosis

`.agents/skills/assess-run/SKILL.md` directs the reviewer to treat every action as the expected output of the harness and forbids attributing error to the agent. That assumption is incompatible with an objective comparison among harness failure, task misunderstanding, and over-generation. This audit follows the operator's request for evidence-based attribution instead. Both harness influence and execution choices remain possible causes.

## What would have made it cheap

Before implementing, identify the remaining gap in one paragraph: the server already reads replies; the browser-only mounting and attribution path prevent useful initial HTML; the live listener runs without an active-session boundary and cleanup. Reuse the existing renderer, reply component, store ordering, and browser links. Verify those changed outcomes with concise scenario tests.

The test plan should identify which assertion fails on the baseline and passes after the correction. It should not invent a framework around platform behavior or require one fixture thread per assertion. The relevant discussion scenarios may reasonably produce approximately seven tests; the scenario inventory and changed behavior determine the count.

## Recommendations

1. Amend the epic's immediate delivery scope. State the baseline, the observable remaining gaps, and the files or application boundaries likely to change. Keep the wider epic outcomes visible without treating them as work in this increment.
2. Amend `.claude/skills/app-e2e/SKILL.md`. Require one concise test per changed application scenario at the cheapest useful layer. A test must fail for a plausible defect in the introduced behavior. Existing behavior and dependency guarantees do not gain tests merely because a new spec describes them.
3. Preserve orchestration-only `first-mate`. Defer a possible scope check before delegation and acceptance of results for later collation. The operator withdrew the inline-work proposal and chose to observe the accepted harness changes before introducing more.
4. Correct `.agents/skills/assess-run/SKILL.md` so an audit may distinguish harness pressure from execution failure. Do not prescribe the cause before examining evidence.
5. Apply `docs/WRITING.md` to the actual comments during implementation. Do not add another prose rule or move every verification gate merely to restate an existing requirement.
6. Use review checks for semantic scope. Require a reason for custom sorting after an ordered query, manual viewport restoration, or a second component lifecycle manager. These are review triggers, not blanket syntax bans.
7. Reuse existing lint/compiler diagnostics. Consider unused-parameter reporting and inspect relevant Svelte reactive-capture warnings. Do not ban all initial-state captures: `DiscussionSection` intentionally initializes local state from server props. No new linter dependency or arbitrary line-count gate is justified by this audit.
8. Prepare a selective reversal manifest before restarting. Preserve unrelated release changes and useful evidence, but reconstruct the implementation from `a84aa111` rather than repairing every abstraction added since then. Execute reversals only after the operator authorizes implementation.

The restart should carry a short definition of done, a changed-scenario test list, and an explicit stop condition. A newly noticed epic outcome should not expand that increment without a scope decision.
